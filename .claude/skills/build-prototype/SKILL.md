# Build Prototype

Skill นี้เป็น workflow มาตรฐานสำหรับสร้าง/ปรับปรุง Clickable HTML Prototype ภายใต้
`docs/02-design/01-prototypes/` จากแหล่งความจริงปัจจุบัน (`feature-list.md`,
`user-journey.md`, `backlog.md`, `DESIGN.md`) ตามกฎใน `CLAUDE.md`

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: ใช้ค่าวันที่ปัจจุบันที่มีอยู่ในบริบทของคุณ (รูปแบบ `YYYYMMDD`)
   เพื่อส่งต่อให้ subagent ใช้ตั้งชื่อโฟลเดอร์เวอร์ชัน/log ของวันนี้ — subagent ไม่มีเครื่องมือ
   Bash จึงหาวันที่เองไม่ได้ ต้องส่งมาให้ใน prompt เสมอ

2. **ตรวจสอบเวอร์ชันเดิมก่อนถามผู้ใช้**: Glob ดูว่ามีโฟลเดอร์ `docs/02-design/
   01-prototypes/*` อยู่แล้วหรือไม่
   - ถ้า**ยังไม่มีเวอร์ชันใดเลย**: ข้ามคำถามข้อถัดไปได้เลย เตรียมสร้างเวอร์ชันแรก
     (`{YYYYMMDD}-01-v1`)
   - ถ้า**มีเวอร์ชันก่อนหน้าอยู่แล้ว**: ใช้ `AskUserQuestion` ถามผู้ใช้ก่อนเรียก subagent
     เสมอว่าต้องการ (ก) สร้างเวอร์ชันใหม่ทั้งหมด (บอกชื่อเวอร์ชันถัดไปที่คำนวณได้ เช่น
     `{YYYYMMDD}-02-v2` ถ้าสร้างวันเดียวกับเวอร์ชันล่าสุด หรือ `{YYYYMMDD}-01-v2` ถ้าคนละวัน),
     (ข) แก้ไขเวอร์ชันล่าสุด (`{ชื่อโฟลเดอร์ล่าสุด}`) ในที่เดิม, หรือ (ค) แก้ไขเวอร์ชันอื่นที่
     ไม่ใช่ล่าสุด (ให้ผู้ใช้ระบุ) — **ถามทุกครั้งที่มีเวอร์ชันอยู่แล้ว ไม่สันนิษฐานเอง** โดย
     **แนะนำตัวเลือก (ข) แก้ไขเวอร์ชันล่าสุดเป็นค่าเริ่มต้นที่แนะนำ** (ต่อท้าย label ด้วย
     "(แนะนำ)") เมื่อผู้ใช้พูดถึงการ "ปรับ/เพิ่มฟีเจอร์" ในของเดิม เพราะรักษาความต่อเนื่องและไม่ต้อง
     สร้างหน้าจอ shared ซ้ำ แต่ถ้าคำขอของผู้ใช้สื่อถึงการเปลี่ยนแปลงใหญ่/รื้อโครงสร้างใหม่ทั้งหมด
     ให้แนะนำ (ก) สร้างเวอร์ชันใหม่แทน — เลือกตัวเลือกแนะนำตามบริบทจริงของคำขอ ไม่ใช่ตายตัวเสมอไป

3. **ส่งต่อให้ subagent `prototype-writer`**: เรียกผ่าน Agent tool
   (`subagent_type: prototype-writer`, รันแบบ foreground คือ `run_in_background: false`
   เพราะ subagent นี้ต้องเสนอแผน scope ให้ผู้ใช้ยืนยันแบบโต้ตอบผ่าน `AskUserQuestion` เสมอ
   ก่อนเขียนไฟล์จริง) โดย prompt ที่ส่งต้องมี:
   - วันที่ปัจจุบัน (YYYYMMDD)
   - โฟลเดอร์เป้าหมายเต็ม (path) และระบุชัดว่าเป็น "เวอร์ชันใหม่ทั้งหมด" หรือ "แก้ไขเวอร์ชันเดิม"
     ตามที่ตัดสินใจในข้อ 2
   - ขอบเขตที่ผู้ใช้ระบุมา (ถ้ามี เช่น "เฉพาะฟีเจอร์การชำระเงิน") มิฉะนั้นแจ้งว่า default คือ
     ครอบคลุมทุก journey ใน `user-journey.md`
   - บริบทว่านี่คือ session สนทนากับผู้ใช้จริง คำถามที่ subagent ถาม (รวมถึงการขอยืนยันแผน
     scope) จะไปถึงผู้ใช้ทันที ไม่ใช่ mock/สมมติคำตอบเอง

4. **รอผลลัพธ์**: เพราะรันแบบ foreground เทิร์นนี้จะได้รับผลลัพธ์ก่อนตอบผู้ใช้ต่อ ระหว่างที่
   subagent เสนอแผน scope หรือถามคำถามอื่น ให้ปล่อยให้ subagent จัดการเอง อย่ายืนยัน/ตอบ
   แทนผู้ใช้

5. **ตรวจจับสัญญาณ "ต้องการ Design System" แล้ว auto-chain**: อ่านรายงานที่ได้กลับมาจากข้อ 4 ทั้งหมด
   - **ถ้าไม่มีหัวข้อ `## NEEDS_DESIGN_SYSTEM` ในรายงาน**: ข้ามไปข้อ 6 ตามปกติ
   - **ถ้ามีหัวข้อนี้**: แปลว่า `DESIGN.md` ยังไม่พร้อมและ subagent ยังไม่ได้เขียนไฟล์ HTML ใดๆ
     ให้ทำตามลำดับนี้:
     a. แจ้งผู้ใช้สั้นๆ ก่อนว่ายังไม่มี Design System ที่ใช้ได้ กำลังส่งต่อให้ `create-design-system`
        จัดการให้อัตโนมัติ แล้วจะกลับมาทำ prototype ต่อ (ไม่ต้องถามผู้ใช้ก่อนว่าจะส่งต่อหรือไม่ —
        เป็นพฤติกรรมมาตรฐานของ skill นี้)
     b. เรียก skill `create-design-system` โดยส่งบริบทต่อไปนี้ให้ครบ: เนื้อหาทั้งหมดใต้หัวข้อ
        `## NEEDS_DESIGN_SYSTEM` แบบ verbatim (ไม่สรุปย่อเอง), วันที่ปัจจุบัน (YYYYMMDD),
        ขอบเขต prototype ที่รออยู่ และรายการองค์ประกอบ UI ที่ต้องใช้ เพื่อให้ §8 ครอบคลุมของจริง,
        และบริบทว่าถูก auto-chain มาจาก `build-prototype` ไม่ใช่ผู้ใช้สั่งตรงๆ
     c. รอผลลัพธ์ แล้วสุ่มตรวจเองอย่างน้อย 1 จุด (เปิดอ่าน `DESIGN.md` จริงว่ามีหัวข้อ §1–§11
        ครบ และ token สีมีค่าครบทั้งธีมมืดและธีมสว่าง) ก่อนไปขั้นตอนถัดไป
     d. เรียก subagent `prototype-writer` **อีกรอบ** ด้วย prompt เดิมจากข้อ 3 บวกข้อความแจ้งว่า
        `DESIGN.md` พร้อมแล้ว และแนบแผน scope ที่ subagent เตรียมไว้แล้วในรอบก่อน เพื่อไม่ให้
        ต้องวางแผนและขอยืนยันจากผู้ใช้ซ้ำอีกรอบโดยไม่จำเป็น
     e. **ป้องกัน infinite loop**: ทำข้อ 5 ซ้ำได้อีกไม่เกิน 1 รอบเท่านั้น (รวมแล้วเรียก
        `prototype-writer` ได้สูงสุด 3 ครั้งต่อ 1 คำขอผู้ใช้) ถ้ารอบที่สองยังพบ
        `## NEEDS_DESIGN_SYSTEM` อีก ให้หยุด auto-chain แล้วรายงานผู้ใช้ตรงๆ ว่า Design System
        ยังไม่พร้อม ให้ผู้ใช้ตรวจสอบเองก่อนสั่งต่อ อย่าวนไม่รู้จบ

6. **ตรวจสอบผลลัพธ์ก่อนรายงาน**: หลัง subagent รายงานว่าสร้าง/แก้ไขอะไรไปบ้าง ให้สุ่ม
   ตรวจสอบเองอย่างน้อย 1-2 จุด (เปิดโฟลเดอร์เวอร์ชันจริงว่ามีไฟล์ตามที่รายงานหรือไม่ เปิดอ่าน
   1-2 หน้าจอตรวจว่าอ้างอิง `style.css`/DESIGN token ถูกต้อง ลิงก์ระหว่างหน้าไม่ตาย)
   ก่อนสรุปให้ผู้ใช้ฟัง ห้ามเชื่อรายงานของ subagent 100% โดยไม่ตรวจเอง — ถ้าสะดวกและผู้ใช้
   ต้องการ สามารถเสนอเปิดตรวจด้วยเบราว์เซอร์จริงในเทรดหลักเป็นขั้นต่อไปได้ (ไม่ใช่ default
   บังคับ เพราะ subagent เองไม่มีเครื่องมือนี้)

7. **สรุปให้ผู้ใช้ทราบ**: หลัง subagent ทำงานเสร็จและตรวจสอบแล้ว ให้สรุปสั้นๆ ว่า
   - สร้างเวอร์ชันใหม่หรือแก้เวอร์ชันเดิม โฟลเดอร์ไหน (path เต็ม)
   - ไฟล์ใดถูกสร้าง/แก้ไขบ้าง พร้อม journey/FR ที่ครอบคลุม
   - จุดที่ถาม/รอผู้ใช้ตัดสินใจระหว่างทาง (ถ้ามี)
   - **Design System ที่ถูก auto-chain ไปสร้าง/ปรับปรุงระหว่างทาง (ถ้ามี)** พร้อมการตัดสินใจหลัก
     ของผู้ใช้เรื่องโทนสีและฟอนต์ที่ได้จากขั้นตอนนั้น
   - ปัญหาเชิงโครงสร้างอื่นที่ subagent รายงาน (เช่น feature-list ไม่ตรงกับ backlog,
     DESIGN.md ว่างเปล่า)

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วเขียนไฟล์ HTML เองตรงๆ ในเทรดหลัก — subagent คือแหล่ง
  ความจริงเดียวของกฎการแปลง feature/journey เป็นหน้าจอตาม DESIGN.md
- **Subagent ต้องเสนอแผน scope ให้ผู้ใช้ยืนยันก่อนเขียนไฟล์ HTML จริงเสมอ** ถ้าผลลัพธ์ที่ได้
  กลับมาแสดงว่า subagent เขียนไฟล์โดยไม่มีการขอยืนยันแผนก่อนเลย ให้ถือว่าผิดกฎ หยุดและแจ้ง
  ผู้ใช้ทันที
- Subagent นี้ตั้งใจไม่มีเครื่องมือ Bash และห้ามแตะไฟล์ใดๆ นอกจากภายในโฟลเดอร์เวอร์ชัน
  prototype เป้าหมายเดียว กับไฟล์ log ของวันนั้น หากผลลัพธ์พูดถึงการแก้ไขไฟล์อื่นนอกเหนือ
  จากนี้ (โดยเฉพาะ `backlog.md`, `feature-list.md`, `user-journey.md`, `DESIGN.md`, หรือ
  ไฟล์ใน `01-spec/`) ให้หยุดและแจ้งผู้ใช้ทันที
- ถ้า subagent รายงานว่า `feature-list.md`/`user-journey.md` ไม่ตรงกับ `backlog.md` หรือ
  `backlog.md` ไม่ตรงกับ spec — ให้แจ้งผู้ใช้ตามที่ subagent แนะนำ (รัน `sync-feature-journey`/
  `audit-backlog` ก่อน) อย่าฝืนสร้าง prototype ต่อในสถานะที่ไม่พร้อม
- ถ้า subagent รายงานว่า `DESIGN.md` หาไม่เจอ ว่างเปล่า หรือขาด token หลัก — **อย่าแจ้งผู้ใช้ให้ไป
  เขียนไฟล์นี้เอง และอย่าเขียนไฟล์นี้เองในเทรดหลัก** ให้ auto-chain ไป `create-design-system`
  ตามข้อ 5 ซึ่งจะสัมภาษณ์ผู้ใช้เรื่องโทนสี สไตล์ และรับภาพ/โลโก้ แล้วสร้าง `DESIGN.md` ให้
  (agent `design-system-writer` เป็นเจ้าของไฟล์นี้เพียงตัวเดียวในระบบ)
- **การถามเรื่อง version folder ในข้อ 2 ต้องทำทุกครั้งที่มีเวอร์ชันอยู่แล้ว ไม่มีข้อยกเว้น** แม้ผู้ใช้
  จะเพิ่งสั่งสร้าง prototype ไปในเทิร์นก่อนหน้าก็ตาม และต้องมีคำแนะนำว่าควรเลือกแบบใดพร้อมเหตุผล
  เสมอ ห้ามเสนอตัวเลือกแบบไม่มีความเห็น
- ถ้า subagent รายงานว่าหาโฟลเดอร์ `docs/02-design/` หรือโครงสร้างที่คาดไว้ไม่เจอ อย่าให้
  subagent ลองสร้าง/ย้าย/เดาชื่อโฟลเดอร์เอง ให้ผู้ใช้เข้ามาตรวจสอบโครงสร้างจริงก่อน
