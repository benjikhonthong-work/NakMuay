# Create Design System

Skill นี้เป็น workflow มาตรฐานสำหรับสร้าง/ปรับปรุง `docs/02-design/DESIGN.md` ซึ่งเป็นแหล่ง
ความจริงเดียวของภาพทั้งหมดในโปรเจกต์ ตามกฎใน `CLAUDE.md`

`DESIGN.md` เป็นไฟล์เดียวในระบบเอกสารนี้ที่ **derive จาก FR/NFR แบบ mechanical ไม่ได้** เพราะ
โทนสีและสไตล์เป็นการตัดสินใจเชิงแบรนด์ที่ต้องมาจากผู้ใช้ skill นี้จึงมีหน้าที่พาผู้ใช้ตัดสินใจให้ครบ
แล้วแปลงเป็น token ที่ใช้งานได้จริง ไม่ใช่โยนงานกลับไปให้ผู้ใช้เขียนเอง

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: ใช้ค่าวันที่ปัจจุบันที่มีอยู่ในบริบทของคุณ (รูปแบบ `YYYYMMDD`) เพื่อส่งต่อให้
   subagent ใช้กับไฟล์ log ของวันนี้ — subagent ไม่มีเครื่องมือ Bash จึงหาวันที่เองไม่ได้
   ต้องส่งมาให้ใน prompt เสมอ

2. **ตรวจสถานะไฟล์เดิมก่อนเรียก subagent**: อ่าน `docs/02-design/DESIGN.md`
   - **ยังไม่มีไฟล์ หรือไฟล์ว่างเปล่า**: เตรียมสร้างใหม่ทั้งไฟล์ ส่งบริบทนี้ไปให้ subagent
   - **มีเนื้อหาอยู่แล้ว**: ใช้ `AskUserQuestion` ถามก่อนเรียก subagent เสมอว่าต้องการ
     (ก) แก้เฉพาะบางหัวข้อ (ให้ผู้ใช้ระบุว่าหัวข้อใด), (ข) เขียนใหม่ทั้งไฟล์และเก็บของเดิมไว้ใน
     `docs/00-archived/`, หรือ (ค) ยกเลิก ไม่แก้อะไร — **แนะนำตัวเลือก (ก) เป็นค่าเริ่มต้น**
     (ต่อท้าย label ด้วย "(แนะนำ)") เพราะการเขียนใหม่ทั้งไฟล์จะทำให้ token ที่ prototype
     เวอร์ชันเดิมใช้อยู่เปลี่ยนไปทั้งหมด เว้นแต่ผู้ใช้สื่อชัดว่าต้องการรื้อแบรนด์ใหม่ทั้งหมด
     จึงแนะนำ (ข) แทน

3. **รวบรวมวัตถุดิบที่ผู้ใช้ให้มา**: ถ้าผู้ใช้แนบภาพตัวอย่าง โลโก้ หรือ moodboard มาในบทสนทนา
   ให้ส่ง path หรือเนื้อหาที่อ่านได้ต่อไปให้ subagent ทั้งหมด ถ้าไม่มี ไม่ต้องทวงถาม — subagent
   จะสัมภาษณ์เอาเอง

4. **ส่งต่อให้ subagent `design-system-writer`**: เรียกผ่าน Agent tool
   (`subagent_type: design-system-writer`, รันแบบ foreground คือ `run_in_background: false`
   เพราะ subagent นี้ต้องสัมภาษณ์ผู้ใช้แบบโต้ตอบผ่าน `AskUserQuestion` เสมอก่อนเขียนไฟล์)
   โดย prompt ที่ส่งต้องมี:
   - วันที่ปัจจุบัน (YYYYMMDD)
   - สถานะของ `DESIGN.md` และแนวทางที่ผู้ใช้เลือกในข้อ 2
   - วัตถุดิบจากผู้ใช้ตามข้อ 3 (ถ้ามี)
   - บริบทว่าถูกเรียกมาจากไหน — ผู้ใช้สั่งตรงๆ หรือถูก auto-chain มาจาก `build-prototype`
     (ถ้าเป็นอย่างหลัง ให้ระบุด้วยว่า prototype ที่รออยู่มีขอบเขตเป็นอะไร เพื่อให้ §8 องค์ประกอบ
     UI ครอบคลุมสิ่งที่ prototype นั้นต้องใช้จริง)
   - บริบทว่านี่คือ session สนทนากับผู้ใช้จริง คำถามที่ subagent ถามจะไปถึงผู้ใช้ทันที
     ไม่ใช่ mock/สมมติคำตอบเอง

5. **รอผลลัพธ์**: เพราะรันแบบ foreground เทิร์นนี้จะได้รับผลลัพธ์ก่อนตอบผู้ใช้ต่อ ระหว่างที่
   subagent สัมภาษณ์ผู้ใช้ ให้ปล่อยให้ subagent จัดการเอง **ห้ามตอบแทนผู้ใช้เรื่องโทนสีหรือสไตล์
   เด็ดขาด** — นั่นคือการตัดสินใจที่ทั้ง skill นี้มีอยู่เพื่อดึงมาจากผู้ใช้

6. **ตรวจสอบผลลัพธ์ก่อนรายงาน**: หลัง subagent รายงานว่าสร้าง/แก้อะไรไปบ้าง ให้สุ่มตรวจเอง
   อย่างน้อย 1-2 จุด (เปิดอ่าน `DESIGN.md` จริงว่ามีหัวข้อ §1–§11 ครบ, ทุก token สีมีค่าครบทั้ง
   ธีมมืดและธีมสว่าง, §8 อ้างถึงองค์ประกอบที่ปรากฏจริงใน `user-journey.md`) ก่อนสรุปให้ผู้ใช้ฟัง
   ห้ามเชื่อรายงานของ subagent 100% โดยไม่ตรวจเอง

7. **สรุปให้ผู้ใช้ทราบ**: 
   - `DESIGN.md` ก่อนเริ่มงานอยู่ในสถานะใด และตอนนี้มีหัวข้อใดครบแล้ว
   - การตัดสินใจหลักที่ผู้ใช้เลือก (โทนสี ธีมเริ่มต้น ฟอนต์ ความหนาแน่น สไตล์องค์ประกอบ)
   - **ย้ำให้ผู้ใช้ทราบว่าค่าคอนทราสต์เป็นการประเมิน ยังไม่ได้วัดด้วยเครื่องมือจริง** และควรวัดซ้ำ
     ก่อนใช้งานจริง
   - ผลกระทบต่อ prototype เวอร์ชันเดิม ถ้ามี token ที่ถูกใช้อยู่ถูกเปลี่ยน
   - ถ้าถูก auto-chain มาจาก `build-prototype` ให้แจ้งว่ากำลังกลับไปทำ prototype ต่อ

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วเขียน `DESIGN.md` เองตรงๆ ในเทรดหลัก — `design-system-writer`
  คือ agent เดียวในระบบที่มีสิทธิ์เขียนไฟล์นี้ และเป็นแหล่งความจริงเดียวของกฎว่า Design System
  ต้องมีหัวข้ออะไรครบบ้าง
- **ห้ามตัดสินใจเรื่องโทนสี ฟอนต์ หรือสไตล์แทนผู้ใช้ ไม่ว่าจะดูชัดเจนแค่ไหน** ถ้าผู้ใช้ไม่ตอบหรือ
  ตอบว่า "แล้วแต่" ให้ subagent เสนอชุดตัวเลือกที่เจาะจงพร้อมข้อดีข้อเสียให้เลือก ไม่ใช่เลือกให้เอง
- Subagent ตั้งใจไม่มีเครื่องมือ Bash และห้ามแตะไฟล์ใดๆ นอกจาก `DESIGN.md` กับไฟล์ log ของวันนั้น
  หากผลลัพธ์พูดถึงการแก้ไขไฟล์อื่น (โดยเฉพาะ `backlog.md`, `feature-list.md`, `user-journey.md`,
  ไฟล์ใน `01-spec/` หรือไฟล์ใน `01-prototypes/`) ให้หยุดและแจ้งผู้ใช้ทันที
- ถ้า subagent รายงานว่าค่าสีที่ผู้ใช้เลือกไม่ผ่านเกณฑ์คอนทราสต์และผู้ใช้ยืนยันจะใช้ค่านั้น
  ให้บันทึกไว้ในสรุปอย่างชัดเจนว่าเป็นการยอมรับความเสี่ยงโดยผู้ใช้ ขัดกับ NFR ด้านการเข้าถึง
  อย่าปล่อยผ่านเงียบๆ
- ถ้า subagent รายงานว่าหาโฟลเดอร์ `docs/02-design/` ไม่เจอ อย่าให้ subagent ลองสร้าง/ย้าย/
  เดาชื่อโฟลเดอร์เอง ให้ผู้ใช้เข้ามาตรวจสอบโครงสร้างจริงก่อน
